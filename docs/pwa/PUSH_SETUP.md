# atlas — installable app + push notifications: go-live steps

Branch `feat/pwa-install-push` (version A, PR A) / `feat/pwa-install-push-b` (version B, PR B).
Nothing below has been done in production. Every step needs Deen's approval.

Until these steps are done the merged code is safe: the install offer works (it needs nothing on the server),
and the "הפעל התראות" button is hidden ("יהיה זמין בקרוב" in Settings) because there is no `VITE_VAPID_PUBLIC_KEY`.

## Order

1. **VAPID keys (once per environment)** — on any machine with Node:
   ```bash
   npm run push:vapid
   # prints {"publicKey": "...", "privateKey": "...", "subject": "mailto:support@atlas-il.com"}
   ```
   The private key is a secret. Never commit it, never put it in a `VITE_` variable.
   Rotating it later invalidates every device subscription (owners tap "הפעל התראות" again).

2. **Supabase Edge Function secrets** (Dashboard → Edge Functions → Secrets, or CLI):
   ```bash
   supabase secrets set VAPID_PUBLIC_KEY=<publicKey> VAPID_PRIVATE_KEY=<privateKey> VAPID_SUBJECT=mailto:support@atlas-il.com
   ```
   `ATLAS_CRON_SECRET` already exists (used by ical-sync / automation-runner) and is reused.

3. **Deploy the function** (no JWT check at the gateway: the DB trigger calls it with the `x-atlas-cron` secret,
   same as ical-sync; the Settings test call is checked inside the function):
   ```bash
   supabase functions deploy send-push --no-verify-jwt
   ```

4. **Apply the migration** `supabase/migrations/022_push_notifications.sql` (back up first, as on release nights).
   Additive only: table `push_subscriptions` + RLS, RPC `push_subscribe`, trigger function `atlas_push_on_insert`,
   AFTER INSERT triggers on `bookings` and `leads`. Re-runnable. Rollback statements are at the end of the file.
   Needs 015 (atlas_call_edge + Vault secret `atlas_cron_secret`) and 014 — both are live.
   Order matters: deploy the function (3) before the migration, otherwise the first trigger calls hit a missing
   function (harmless — pg_net just logs a 404 — but no notification).

5. **Vercel env** `VITE_VAPID_PUBLIC_KEY=<publicKey>` (Production + Preview), then redeploy.
   This is what makes the "הפעל התראות" button appear.

6. **Smoke test on a real phone**
   - Android Chrome: atlas-il.com → sign in → /today → "התקנה" → "הפעל התראות" → Settings → התראות → "התראת ניסיון".
   - iPhone (iOS 16.4+): Safari → atlas-il.com → Share → "הוספה למסך הבית" → open from the icon → "הפעל התראות".
   - Server path: create a booking from the direct-booking page (/book/<slug>) on another device → the phone gets
     "הזמנה חדשה מדף ההזמנות". Or, with a user JWT:
     ```bash
     curl -X POST https://romvmqbcinurscwdsskx.supabase.co/functions/v1/send-push \
       -H "Authorization: Bearer <user access token>" -H "Content-Type: application/json" -d '{"test": true}'
     ```
   - Check `select * from push_subscriptions` shows the device, and `net._http_response` shows 200s from send-push.

## Who gets notified (rules in send-push)

| Event | Notified | Not notified |
|---|---|---|
| Booking from the direct-booking page, API, or a teammate | every enabled device of the organization | the user who typed it in (their own devices) |
| Booking that arrived through iCal (Booking.com / Airbnb / other) | every enabled device, tag per calendar (they replace each other instead of piling up) | the first import of a newly connected calendar; past stays; cancelled rows |
| New lead | devices with "ליד חדש" on | — |

Each device chooses bookings / channel bookings / leads in Settings → התראות.
Dead subscriptions (404/410 from Apple/Google) are deleted; 5 failures in a row disable the device.

## The service worker change (please review)

The site has ONE service worker (`/sw.js`, generated by vite-plugin-pwa / Workbox, scope `/`, shared by landing and app).
A separate app-only worker is not possible: the app routes (/today, /calendar…) live at the root next to the landing,
and only one worker can control a scope. So push is added as an isolated file:

- `vite.config.js` → `workbox.importScripts: ['/push-sw.js']` (the generated sw.js gets one `importScripts("/push-sw.js")` line)
- `public/push-sw.js` adds only `push`, `notificationclick`, `pushsubscriptionchange` listeners. No `fetch` handler,
  no cache. Not precached (`globIgnores`), served no-cache, so it updates with every deploy.
- Checked locally: landing renders with 0 console errors under the new worker, Chrome reports 0 installability errors,
  the worker has no extra fetch listener (qa/pwa/installability-a.json, -b.json).
- To remove push entirely: delete the `importScripts` line (and the file). Nothing else in the worker depends on it.
